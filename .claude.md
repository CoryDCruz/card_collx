# Card Collection Tracker - Project Context

## Project Overview

A mobile-first web application for tracking and managing sports card collections. Users can scan cards using their iPhone camera, catalog them, and use AI agents to discover average market prices.

## Goals

1. **Card Scanning**: Use phone camera to capture card images
2. **Cataloging**: Store and organize card collection with metadata
3. **AI Price Discovery**: Use AI agents to find average sell prices from multiple sources
4. **Mobile Experience**: iPhone-optimized with PWA support (future)

## Tech Stack

### Backend
- **FastAPI** - Python web framework
- **SQLAlchemy** - ORM for database operations
- **Pydantic** - Data validation and settings
- **SQLite** locally / **PostgreSQL** (Supabase) in production — via `DATABASE_URL`
- **S3-compatible storage** (Supabase Storage) in production, local filesystem in dev — via `STORAGE_TYPE`
- **OpenAI Vision API** (GPT-4o) - Card metadata extraction from images
- **gunicorn + uvicorn** - Production server (Render)
- **Python 3.8+**

### Frontend
- **React** - UI framework
- **TypeScript** - Type safety
- **Vite** - Build tool and dev server
- **Axios** - HTTP client
- **Node.js 20+**

### Future Integrations
- **LangChain/CrewAI** - AI agents for price discovery

## Environment Variables

### Backend (.env)
- `DATABASE_URL` - Database connection string
- `STORAGE_TYPE` - `local` (default) or `s3`
- `S3_ENDPOINT_URL` - S3-compatible endpoint (e.g. Supabase, R2)

- `S3_BUCKET_NAME` / `S3_PUBLIC_URL` - Bucket name and public URL

- `ALLOWED_ORIGINS` - CORS origins

### Frontend (.env)
- `VITE_API_URL` - Backend API URL (default: http://localhost:8000/api)

## Image Processing Details

### Storage Architecture
- **Abstract Interface**: `StorageBackend` with two implementations
- **Local**: Files in `uploads/{card_id}/{filename}`, async via `aiofiles`
- **S3**: Keys at `cards/{card_id}/{filename}`, via boto3 (works with Supabase, R2, AWS)
- **Factory**: `get_storage_backend()` in `storage/__init__.py` picks based on `STORAGE_TYPE`
- **Vision pipeline**: `save_card_image_with_bytes()` captures processed bytes in memory for Vision API — avoids file path dependency

### Image Processing Pipeline
1. **Validation**: File type, size (10MB max), and integrity checks
2. **Optimization**: Resize to max 1024x1024 pixels (aspect ratio preserved)
3. **Compression**: Convert to JPEG at 85% quality
4. **Filename Generation**: `{timestamp}_{hash}_{sanitized_name}.jpg` for uniqueness
5. **Storage**: Save to organized directory structure
6. **Database**: Update card record with `image_url` field

### Error Handling
- Invalid files rejected with clear error messages (400 Bad Request)
- Files too large rejected (413 Payload Too Large)
- Automatic cleanup of orphaned database records if image processing fails
- Image deletion cascades when card is deleted

## Render Deployment Steps

### 1. Create Web Service on Render
- Go to render.com → New → Web Service
- Connect GitHub repo: `CoryDCruz/card_collx`
- **Root Directory**: `backend`
- **Runtime**: Python 3
- **Build Command**: `pip install -r requirements.txt`
- **Start Command**: auto-detected from Procfile (`gunicorn app.main:app --workers 1 --worker-class uvicorn.workers.UvicornWorker --bind 0.0.0.0:$PORT --timeout 120`)

### 2. Set Environment Variables on Render
| Variable | Value |
|---|---|
| `DATABASE_URL` | Supabase PostgreSQL connection string |
| `STORAGE_TYPE` | `s3` |
| `S3_ENDPOINT_URL` | Supabase Storage endpoint |
| `S3_ACCESS_KEY_ID` | Supabase service role key |
| `S3_SECRET_ACCESS_KEY` | Supabase service role key |
| `S3_BUCKET_NAME` | Bucket name (e.g. `card-images`) |
| `S3_PUBLIC_URL` | Public URL for the bucket |
| `OPENAI_API_KEY` | OpenAI API key |
| `ALLOWED_ORIGINS` | `https://card-collx.vercel.app` |

### 3. Deploy and Verify
- Trigger deploy
- Check `/health` endpoint on Render URL
- Test `/docs` to confirm API is live

### 4. Update Frontend (Vercel)
- Set `VITE_API_URL` on Vercel to Render backend URL (e.g. `https://card-collx.onrender.com/api`)
